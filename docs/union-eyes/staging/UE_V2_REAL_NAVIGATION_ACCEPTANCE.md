# Real-provider navigation qualification

The main-only protected `ue-v2-staging-real-navigation.yml` uses existing named synthetic Entra identities selected by the requested role. It creates a real authorization-code session, requires the live application's exact authorized source, checks source-file digests, observes the role execution home and visits every visible canonical destination in EN/FR on desktop and mobile. Mobile checks include actual horizontal overflow. The role input describes a separately qualified, live canonical membership; it does not issue a role, session, office or mandate.

The source-derived inventory records 42 canonical menu entries across five experiences (with 32 unique paths), superseding the historical 43-entry count for this exact source only. The source-derived profiles now include member, steward, chief steward, officer, secretary-treasurer, organization admin and explicitly provisioned platform owner. A profile is an expectation, not evidence that its fixture has that authority. Every run must first match the live canonical role. Visibility follows the current server-role and pilot policy. A verified officer's Finance entry is hidden. Organization administration exposes only its directly eligible destinations; platform-only operations, user management, security and integrations must remain denied. Officer deep links cover the ordinary governance trust and intelligence shells without creating any institutional mandate.

Named member, steward, secretary-treasurer and organization-admin fixtures retain their existing memberships. The senior-representative and officer tests share the existing A identity; a private operator must record any exact synthetic role transition and restore its original officer role after qualification. A platform-owner test is eligible only after explicit synthetic platform-operator provisioning; the pre-existing `system_admin` organization label with `is_system_admin=false` is not platform authority and must not be treated as one. No runner can assign roles, change identity bindings or manufacture sessions.

Finance/dues persistence and Financial Officer 2.1 are excluded from this base release by the owner's November 13 scope correction. Positive finance feature navigation is explicitly skipped and receives no acceptance credit. All eligible fixtures, including high-ranked ones without a financial mandate, must receive HTTP 403 from `/api/finance/summary` and `/api/finance/per-capita/inbound`. Roles that cannot see the finance shell must also complete the restricted-route denial. This keeps sensitive financial boundaries mandatory without implementing or qualifying excluded financial workflows.

The inventory generator derives profiles from the application's actual role/navigation policy and checks the committed snapshot in the protected workflow. Its source digests remain bound to the unchanged deployed application candidate; tooling-only changes do not create a new deployed candidate.

Each positive destination requires an actual HTTP 200, exact final route, no Next error page, and successful mobile rendering. Expected denials cannot substitute for positive availability claims. Platform- or mandate-restricted entries remain unqualified for positive use and must retain their conservative registry status. Source and local syntax validation do not establish deployed acceptance; preserve actual receipts before updating readiness.
