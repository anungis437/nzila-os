# Convergence tranche 10b: the enhanced RBAC relations exist, and the code that uses them runs

Date: 2026-11-02. Branch `agents/ue-cursor-final-closure`. Base commit `39403a3b1`; source commit: see the ledger entry `UE-ENHANCED-RBAC-RELATIONS-20261102`.
Platform migrations `0075_enhanced_rbac_relations`, `0076_enhanced_rbac_catalog`; cache migration `0053_enhanced_rbac_rls_closure`.
Credit: none (cross-cutting source evidence, `defectCredit` 0, `closureCredit` 0). Nothing is closed. `READY_FOR_STAGING` stays `NO`.
This tranche acts on the direction "missing, rbac is needed" (and "address all the missing tables, columns etc"): the enhanced RBAC was declared and used, and did not exist.

## What was wrong

- `role_definitions`, `member_roles`, `permission_exceptions` and `rbac_audit_log` were named by `db/queries/enhanced-rbac-queries.ts`, imported by `lib/api-auth-guard.ts` (`withEnhancedRoleAuth`, `withPermission`,
  `withScopedRoleAuth`) and `lib/enterprise-role-middleware.ts`, and classified nowhere: no Drizzle declaration, no platform migration, no Django model, no storage-authority entry. Every call would have failed with
  "relation does not exist"; `logPermissionCheck` is fire-and-forget, so the audit failure was swallowed.
- The query module itself could not have worked had the tables existed: a raw `SELECT *` returned snake_case while the interfaces were camelCase; `INTERVAL '${hours} hours'` cannot bind a parameter; two views it read
  (`v_active_member_roles`, `v_upcoming_elections`) existed nowhere; the "hash chain" was a base64 prefix of the previous hash and verified nothing; writes ran under the tenant role and named no organization.
- No route adopts the enhanced wrappers (a product decision, left as it is): the capability is the library path, so nothing user-visible depended on it, and nothing could.

## What changed

**Relations** (Drizzle `db/schema/domains/member/enhanced-rbac.ts`, platform 0075 generated by `generate-relation-create.ts`, 17 + 33 + 21 + 34 columns):
`role_definitions` (the catalog; no tenant column: a role code means one thing everywhere), `member_roles` (scope, term, approval, acting; a partial unique index on a live assignment), `permission_exceptions`
(time- and use-limited, revocable), `rbac_audit_log` (append-only; identity `sequence_number` gives the chain its order; no foreign key on `organization_id`, because evidence carries identifiers).
CHECK constraints hold the rules the module used to assume: status and assignment-type sets, a term does not end before it starts, vote counts consistent, an approval-required role is not `active` without an approver, an
exception expires after it starts and a revoked one is not active, a review has both a time and a reviewer.

**Authority** (manifest, `db/rls-storage-authority/organizations-membership.ts`; catalog contract regenerated, 878 entries, digest `b93abf51973eb40ef693fab45b829ae49987b969dd970a55ae8e1f811d65619a`): `role_definitions` is
GLOBAL_REFERENCE_DATA; the other three are TENANT_RLS_REQUIRED through the existing direct-organization policy (cache 0053 uses `ue_create_direct_org_rls_policy`, FORCE RLS). **The tenant runtime role holds SELECT only on all four.**
Assigning, approving, revoking, granting an exception, counting its use and writing an audit entry run under the system role and name the organization they mean: authorization state never changes through a tenant-scoped
connection. The system role holds SELECT, INSERT and UPDATE and no DELETE or TRUNCATE.

**Integrity in the database (0076).** `rbac_audit_log` refuses DELETE and TRUNCATE for every role including the owner, and refuses any UPDATE but recording a review, once (`restrict_violation`). A trigger on `member_roles`
and `permission_exceptions` refuses a member who does not belong to the row's organization (and an acting-for member of another organization) and, for a role, one that is not an active role of the catalog. The catalog is seeded
with the 11 organization roles of the code (`TENANT_LOCAL_ROLES` in `lib/auth/roles.ts`: admin, president, vice_president, secretary_treasurer, chief_steward, officer, clerk, steward, bargaining_committee,
health_safety_rep, member) at the level `getRoleLevel()` gives and the permissions `ROLE_PERMISSIONS` gives. **The Nzila platform-operations and CLC/federation/national roles are deliberately not seeded**: `member_roles`
is tenant data, and a platform role in it would be an escalation path. A custom role that already uses a seeded code stops the migration; nothing is overwritten.

**The module, rewritten.** camelCase at the row boundary (numeric and bigint to numbers, timestamps and dates to `Date`); the two views inlined with one definition of "live role" (active, begun, not ended, inside an
acting window, through an active role definition) and one of "live exception"; `isMemberRowId` (the guard's `auth-org:<id>` and `platform-admin` contexts are not members and hold no rows); writes under the system role,
each naming its organization; the audit chain is SHA-256 over the previous hash and the decision's fields, written under a per-organization advisory lock so the identity column is the order they were linked in, and
`verifyAuditLogIntegrity` recomputes every hash from the stored columns, so an edited or deleted entry, not only a broken link, is found (paged, carrying the previous hash across pages). New: `approveMemberRole`,
`markAuditEntryReviewed`, `findLivePermissionException`. Signatures changed: `updateMemberRole`, `revokeMemberRole`, `revokePermissionException` and `incrementExceptionUsage` take the organization;
`incrementExceptionUsage` returns whether the use was counted and never passes the limit. `lib/enterprise-role-middleware.ts` uses `findLivePermissionException`, counts the use, treats an exception that ran out between
the lookup and the count as no grant, and fails closed, with a log line, when a lookup fails.

## What the native proof found that no mock could

The native test (`db/__tests__/enhanced-rbac.postgres.test.ts`) runs the module and the middleware unmodified as the real `union_eyes_runtime` and `union_eyes_system` roles, through the postgres.js driver the application
uses. It found, in order, and each is fixed and pinned:

1. **Every audit write threw `ERR_INVALID_ARG_TYPE`**: a raw `Date` in a drizzle `sql` template over postgres.js. A platform-wide class, closed at the client (tranche 10c).
2. Temporal columns returned by a raw `execute` are the server's text, not `Date` as the interfaces say: mapped at the row boundary.
3. `sequence_number` (bigint) arrived as a string: mapped.
4. `revokeMemberRole` on a role that has not started set `end_date` before `start_date` and the database refused it (`member_roles_end_after_start`): the term now ends at the later of today and its start.
5. A term and an exception defaulted their start from the application clock (`new Date()`), so an exception granted "now" was not yet effective if the clocks differed: the database's `CURRENT_DATE` / `NOW()` start them.
(One more failure was the test's own: aliasing `sequence_number::text` to the same name made `ORDER BY` sort as text. The module was correct: 6 ← null, 7 ← 6, … 15 ← 14 under ten concurrent writers.)

Executing the rollbacks (`db/__tests__/platform-0075-0076.postgres.test.ts`) found two more:

6. **The generated 0075 rollback could never run.** `generate-relation-create.ts --rollback` emitted `FOREACH t IN ARRAY ARRAY[] LOOP` for a set of relations that uses no enum type, and PostgreSQL refuses an untyped
   empty array when the statement runs (`42P18 cannot determine type of empty array`). Every earlier relation set had enums, so it had never shown. The generator now emits the enum loop only when there are enum types
   (output for every earlier set is byte-identical); the regenerated rollback differs from the broken one only by that loop.
7. 0076's statements had no terminating semicolon (the runner splits on the breakpoint marker and does not need one), so its file could not run as one script. Now terminated and regenerated; the lineage hash is updated.
   `db/__tests__/migration-file-shape.test.ts` holds both shapes (no untyped empty array, every chunk terminated) across all 200 platform and cache migration files: no other migration has either.

## What this does not do

- No route adopts the enhanced wrappers; an administrative surface to assign roles is a product decision and not built. No Django model, by design: a Django ViewSet would be a second write path to authorization state.
- **`clerk` is not in `ROLE_HIERARCHY`** (`lib/api-auth-guard.ts`), so every minimum-role check reads it as level 0 although `getRoleLevel` gives it 70; adding it would widen access on finance pages, so it is pinned in
  the consistency test and left for the owner. `ROLE_HIERARCHY` and `getRoleLevel()` also disagree for the platform roles (300 against 250 and similar): flagged, not changed.
- PostgreSQL 15 is not yet run locally (CI runs both). No HTTP-level proof. Exact-SHA CI for the final head and an independent reviewer are outstanding. No defect or CLOSED credit.
