# Privileged-Caller Authority Audit (PR #752)

Source-controlled evidence artifact for every production caller of
`withSystemContext`, `withSystemRLSContext`, or `withPlatformAdminRLSContext`
in `apps/union-eyes`. Generated by manual review (round 6, 2026-09-01) using a
static discovery heuristic (see Methodology) plus individual code-reading
verification of every flagged file — the heuristic is discovery evidence,
not final proof; every disposition below reflects the actual call graph.

**Total callers: 61/61 reviewed.**

## Methodology

1. `rg -l "withSystemContext|withSystemRLSContext|withPlatformAdminRLSContext" -g "*.ts" app lib services actions`,
   excluding `__tests__/`, `.test.ts`, and `lib/db/with-rls-context.ts` (the
   definition file) — 61 files.
2. For each file, static heuristic: does an auth-guard pattern (`requireApiAuth`,
   `withApiAuth`, `withOrganizationAuth`, `crudRoutes`, `withApi`, `hasMinRole`,
   `auth()`, `getUserContext`, cron-secret checks, webhook signature
   verification, `enforcePilotOwnership`) appear in the file text *before* the
   first `withSystemContext(`-style call?
3. **Every file the heuristic did not confidently match was individually
   re-read** to confirm the real call graph, because the textual-order
   heuristic has two known false-positive modes:
   - a mention of `withSystemContext()` inside the file's own JSDoc/comment
     header can match before the real call;
   - a private, non-exported helper function defined earlier in a file but
     only ever invoked from an already-authenticated handler later in the
     same file also produces a false "no guard" flag.

`withSystemContext()` itself is never treated as authorization — it is only
the execution mechanism. The question this audit answers is whether a real
authorization decision (route-level guard, or an explicit in-function check)
happens *before* it runs.

# Explicit Organization-Context Audit (PR #752)

Source-controlled evidence artifact for every production call to the
object-form `withRLSContext({ organizationId: ... }, operation)` overload —
the only call shape where a caller directly supplies the RLS tenant context,
as opposed to the no-argument overload which resolves it internally from
auth metadata.

**Total callers: 5/5 reviewed. 0 raw request-derived organization-context
switches found.**

## Methodology

`rg -c "withRLSContext\s*\(\s*\{" -g "*.ts" app lib services actions`
(excluding tests) found exactly 5 files. For each, traced the source of the
`organizationId` value passed into the context object back to its origin.

**Allowed pattern:** authenticated/session-resolved org → authorization
decision → RLS context.
**Disallowed pattern:** request query/body/path value → directly into RLS
context.

## Table

| Caller | `organizationId` source | Pattern |
| --- | --- | --- |
| actions/analytics-actions.ts (11 call sites) | `auth()` → `userId` → `getCurrentUserOrgId()`. Code comment explicitly states it does **not** trust `auth()`'s own `orgId` claim for Entra-backed sessions. | Allowed |
| actions/rewards-actions.ts (1 call site) | `auth()` → `userId` → `getCurrentUserOrgId()`, same non-trust rationale. | Allowed |
| app/api/documents/repository/route.ts (1 call site) | `withOrganizationAuth(async (request, context) => ...)` — org resolved and verified by the framework wrapper, not read from the request. | Allowed |
| app/api/rewards/export/route.ts (1 call site) | `auth()` → `userId` → `getOrganizationIdForUser(userId)`. Code comment explains the same Entra security-group-GUID-is-not-verified-membership rationale. | Allowed |
| lib/case-assignment-engine.ts (15 call sites) | Takes `organizationId: string` as a **plain function parameter** with an explicit TRUST BOUNDARY comment obligating callers to supply only an independently-verified value (e.g. via `getOrganizationIdForUser()`), never a client-suppliable one. | Allowed by contract — but currently has **zero real production callers** (this module and its sibling `lib/workflow-automation-engine.ts` are `LATENT_UNREACHABLE` per the storage authority manifest's `grievance_assignments`/`deadline_reassignment_convergence` entries), so the contract is not yet exercised in production. Re-verify this file first if it is ever wired into a live route. |

## Result

**0 violations.** No production code path resolves `organizationId` for
`withRLSContext` directly from a request query parameter, body field, or path
segment without first passing through an authentication/authorization step.

## Ratchet

`lib/icra/__tests__/assessment-capability-contract.test.ts` enforces the
narrower ICRA capability contract. A broader structural ratchet for this
exact 5-file list (failing if a 6th direct-context caller appears without a
reviewed entry here) is a natural follow-up for
`scripts/rls-storage-reachability-audit.ts` — not yet implemented as an
automated test as of this artifact's date; treat this document as the
source of truth for the reviewed set until then.
