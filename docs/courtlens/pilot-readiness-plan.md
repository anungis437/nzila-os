# CourtLens Pilot Readiness Plan

## Objective

Define the smallest credible access-to-justice pilot for CourtLens as supervised, review-ready justice operations infrastructure.

Delivery principle: adapt ABR's existing workflow, governance, org-scope, RBAC, AI, and audit structure first; add CourtLens-specific adapters only for documented gaps.

## Buyer Assumptions

Pilot buyer can be one of:

- Legal clinic.
- Union.
- Nonprofit.
- Pro bono organization.
- Parent legal network.

## Pilot Value Core

Pilot must deliver this value chain end-to-end:

- Public intake.
- Matter queue.
- Review packet.
- Human approval.
- Referral/status tracking.

## Pilot Scope (Included)

- ABR reuse audit for pilot workflows before adding CourtLens-specific adapters.
- Public issue intake forms for target practice areas (housing/employment/debt initial set).
- Tenant-scoped matter queue and matter detail view.
- Document submission and linkage to matter.
- Draft review packet generation with source/jurisdiction context placeholders.
- Reviewer approval/rejection workflow for AI-generated packet artifacts.
- Referral lifecycle and status tracking.
- Audit traces for intake, AI generation, reviewer action, and referral updates.
- Bilingual-ready copy scaffolding for core flows.

## Pilot Scope (Excluded)

- Standalone CourtLens runtime model separate from ABR.
- Full parent/network analytics suite.
- Full platform operations console parity with legacy app.
- Advanced support-session workflow.
- Production billing rollout.
- Procurement-grade reporting pack automation.
- Any final legal advice output flow.

## Pilot Workflows

## Workflow A: Public Intake to Queued Matter
1. Public user submits intake.
2. System creates tenant-scoped matter by reusing ABR scoped workflow patterns and links intake payload.
3. Matter appears in tenant queue with urgency/risk indicators.

## Workflow B: Document Intake to Review Packet Draft
1. Public or tenant staff uploads documents.
2. Matter links document artifacts through existing blob/evidence primitives where available.
3. AI packet draft generated by composing existing ABR AI legal actions with draft-only status.

## Workflow C: Human Review and Approval
1. Reviewer opens draft packet.
2. Reviewer verifies facts/sources.
3. Reviewer approves, revises, or rejects draft.
4. Approval decision is audited via existing ABR audit/evidence lineage patterns.

## Workflow D: Referral and Status Tracking
1. Reviewer/staff initiates referral action.
2. Referral status transitions are tracked.
3. Status is viewable through appropriate role surfaces.

## Synthetic Demo Data Requirements

Pilot/demo data must be synthetic only.

Required synthetic sets:

- Housing, employment, and debt intake scenarios.
- Risk-flag variety (eviction risk, income-loss risk, utility-shutoff risk analogs).
- Document bundles per matter type.
- Reviewer personas and role-bound visibility scenarios.
- Referral outcomes across suggested/approved/sent/completed states.

Prohibited:

- Real client identifiers.
- Real legal file content.
- Production tenant data.

## Acceptance Criteria

- Pilot implementation reuses ABR primitives first, with only minimal documented-gap adapters.
- Public intake creates tenant-scoped matter records.
- Matter queue correctly filters to active tenant scope.
- Review packet generation outputs draft-only artifacts.
- Human approval action required before packet is marked externally usable.
- Referral status transitions are persisted and visible by permitted roles.
- Core flow actions are auditable with actor + timestamp + action classification.
- No UI text implies CourtLens is providing final legal advice.

## Smoke Tests (Pilot Gate)

Minimum smoke set:

- ABR-reuse audit checks pass for workflow, org-scope, RBAC visibility, AI composition, and audit lineage.
- Public intake happy-path for each practice area.
- Matter queue listing and detail retrieval for scoped tenant.
- Document upload/link path and packet draft generation.
- Reviewer approval/rejection path updates packet status.
- Referral lifecycle transition path.
- Audit event creation for each critical workflow step.
- Permission redaction check between at least two distinct tenant roles.
- Bilingual label load sanity on core screens.

## Stakeholder Demo Script (Post-Gate Only)

Demo sequence:

1. Explain legal boundary and supervised review posture.
2. Run intake scenario.
3. Show queued matter and risk indicators.
4. Show draft review packet and source/jurisdiction trust signals.
5. Show human reviewer approval step.
6. Show referral/status lifecycle.
7. Show audit trace and role-scoped visibility.

## No-Demo-Until-Passed Gate (Strict)

External stakeholder demos are blocked until:

- Live UI smoke test suite passes.
- ABR-reuse audit checks pass with no duplicate primitive implementation.
- Core pilot acceptance criteria pass.
- Legal boundary checks pass (no AI-lawyer framing).
- Synthetic-data-only verification passes.

If any gate fails, demo remains blocked.
