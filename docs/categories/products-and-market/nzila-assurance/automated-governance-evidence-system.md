# Automated Governance Evidence System

> **Status:** Canonical assurance · **Layer:** Evidence generation · **Inherits:** [../nzila-governance/executable-doctrine-enforcement.md](../nzila-governance/executable-doctrine-enforcement.md), [institutional-certification-framework.md](institutional-certification-framework.md)

This document specifies the **automated governance evidence system**: the architecture by which Nzila systems continuously produce reviewable evidence of their governance posture, deployment legitimacy, doctrine compliance, and continuity safety — without dependence on manual narrative.

The premise: **evidence that requires human assembly will degrade**. Evidence that is produced automatically, signed, retained, and reviewable will sustain.

This system is the substrate that makes certification at C3 and above possible.

---

## 1. Posture

The evidence system:

- **Produces continuously** — evidence is a side effect of normal operation, not a separate task
- **Normalizes structurally** — evidence shapes are stable across products and time
- **Retains immutably** — evidence is signed and append-only where consequential
- **Surfaces reviewably** — evidence is queryable, exportable, and presentable on demand
- **Stays governance-safe** — evidence itself respects aggregation stance and anti-surveillance
- **Refuses inflation** — evidence quality is honest; absence is acknowledged, not papered over

Evidence is the institutional memory of governance discipline.

---

## 2. Evidence Generation Surfaces

Automated evidence is generated at:

| Surface | Examples |
|---------|----------|
| Build time | Dependency manifest, policy lint pass record, schema audit, vocabulary audit |
| Deploy time | Release manifest, environment identity, rollback plan validation, isolation check |
| Runtime | Routing decisions, visibility refusals, authority framing presence, notification rate |
| End-to-end validation | Doctrine assertion outcomes, density audit, cross-isolation test results |
| Governance review | Compliance verdicts, architectural review verdicts, AI governance review records |
| Operational telemetry | Operational calmness signals, escalation cadence, executive surface refresh cadence |

Evidence is produced at every surface where it is possible to do so without governance harm.

## 3. Required Evidence Types

### 3.1 Deployment Evidence
- Release identity (release name, version, originating commit SHA)
- Environment identity (environment name, isolation class, region)
- Manifest of included changes with compliance verdicts
- Sequencing and pacing rationale
- Rollback plan reference and validation status
- Stakeholder visibility actions taken
- Approval record with reviewer identity (role-named, not personally weaponized)

### 3.2 Governance Evidence
- Policy assertions evaluated and outcomes
- Doctrine compliance review verdicts and dimension findings
- Architectural review verdicts where applicable
- Waiver records (with rationale, scope, and expiry)
- Drift events detected and remediation status

### 3.3 UX Evidence
- Density-budget audit outcomes per surface class
- Cognitive load checks for executive surfaces
- Notification arrival rates against ceilings
- Authority framing presence checks
- Composite-score absence checks
- Visual regression outcomes for calmness-bearing surfaces

### 3.4 AI Evidence
- Explainability presence (assumption, horizon, uncertainty fields)
- Authority surface presence and override path validation
- Aggregation stance assertion in inputs and outputs
- Generation-indication presence
- Surveillance-pattern lint outcomes
- Black-box scoring lint outcomes

### 3.5 Continuity Evidence
- Role isolation checks
- Cross-stakeholder isolation test outcomes
- Aggregation-stance type tagging coverage
- Retention policy adherence per data class
- Portability surface presence

### 3.6 Pilot Evidence
- Feature profile validation (which features in scope per pilot)
- Pilot-route gating outcomes
- Pilot-scope visibility assertions
- Pilot-data isolation from production analytics
- Pilot exit governance record

## 4. CI/CD Integration Models

### 4.1 Build-Time Evidence
Generated by CI on every pull request and main-line build:
- Policy lints (surveillance pattern, composite score, authority framing, density budget, vocabulary, orchestration exposure)
- Type-system checks for aggregation-stance tagging
- Schema audits for retention and portability
- Dependency and supply-chain checks
- Vocabulary audit against the doctrine glossary

Build-time evidence is **blocking** where it relates to categorical doctrine violations.

### 4.2 Deploy-Time Evidence
Generated by deployment systems at release execution:
- Release manifest assembly and signing
- Environment identity binding
- Pre-deployment isolation verification
- Rollback plan validation
- Stakeholder visibility action execution
- Post-deployment health verification

Deploy-time evidence is **gating** for legitimacy claims at C3+.

### 4.3 Runtime Evidence
Generated continuously by the running system:
- Routing decisions (role, population, scope) with sample-rate retention
- Visibility refusals (signals withheld and why)
- Authority framing render confirmations
- Notification arrival counters per role/population
- Calmness signal counters (motion events, density measurements at sample surfaces)

Runtime evidence supports continuous attestation; sampling is governed to remain anti-surveillance-safe.

### 4.4 E2E-Generated Evidence
Generated by end-to-end test runs:
- Doctrine assertion outcomes (multi-dimensional posture present, composite score absent, etc.)
- Cross-isolation traversal blocks
- Pilot scope enforcement outcomes
- Recommendation surface explainability presence
- Density and cadence audits

E2E evidence is the principal source of pre-deployment doctrine assurance.

### 4.5 Governance Drift Evidence
Generated by drift detection:
- Doctrinal vocabulary regression
- Policy lint regression
- Audit cadence misses
- Certification tier degradations
- Repeat waivers indicating structural drift

Drift evidence is treated as a leading indicator and is reviewed at scorecard cadence.

## 5. Evidence Quality Standards

Each evidence record carries:

- **Subject** — what is being evidenced (system, surface, release, capability)
- **Class** — which evidence type
- **Outcome** — pass / partial / fail / not-applicable
- **Cited source** — which automated check, review, or telemetry produced it
- **Timestamp** — when produced
- **Scope** — environment, release, product
- **Signature** — for retained, attestation-grade evidence

Records missing any of the above are not assurance evidence; they are signal at best.

---

## 6. Anti-Surveillance in Evidence Itself

Evidence generation honors doctrine. Specifically:

- Runtime evidence about user activity is **aggregated, not individual**
- Reviewer identity in evidence is recorded by role, not personalized for ranking
- Telemetry sampling avoids resolving restricted classes
- Evidence retention horizons follow institutional memory governance
- Evidence storage honors stakeholder isolation

Evidence that violates these would itself be a doctrine violation.

---

## 7. Anti-Patterns

- **Vanity evidence** — generating volume without substance to inflate certification appearance
- **Selective retention** — keeping favorable evidence and discarding unfavorable
- **Manual narration as evidence** — replacing automated checks with after-the-fact prose
- **Overbroad sampling** — runtime evidence that drifts toward individual resolution
- **Unsigned attestations** — evidence used at C4+ without signing infrastructure
- **Evidence as marketing** — extracting evidence into promotional surfaces in ways that erode register
- **Stale evidence presented as current** — using old records to claim a current tier

---

## 8. Discipline

The evidence system's strength is in its honesty and continuity. A system that produces partial evidence honestly is more trustworthy than one that produces complete evidence selectively.

This system is what allows Nzila to say, in front of any external party: *"You don't have to trust us — read the evidence."*
