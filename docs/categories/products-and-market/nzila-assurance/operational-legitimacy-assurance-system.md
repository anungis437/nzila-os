# Operational Legitimacy Assurance System

> **Status:** Canonical assurance · **Layer:** Operational legitimacy assurance · **Inherits:** [../nzila-ip/operational-legitimacy-framework.md](../nzila-ip/operational-legitimacy-framework.md), [../nzila-governance/continuity-safe-deployment-governance.md](../nzila-governance/continuity-safe-deployment-governance.md), [institutional-certification-framework.md](institutional-certification-framework.md)

This document defines assurance standards for **institutional deployment realism and operational legitimacy** — the property that distinguishes a system genuinely operating in real institutions under governance from one that merely demonstrates capability in controlled settings.

It is the model by which Nzila certifies systems under class **Operational Legitimacy Readiness**.

---

## 1. Posture

Operational legitimacy assurance:

- Is **realism-anchored** — assurance verifies that the system operates as represented, in real conditions
- Is **trust-pacing-aware** — legitimacy includes the rhythm at which institutional trust is built
- Is **maturity-honest** — partial maturity is named partial
- Refuses **theater** — demonstrations, dashboards, and rollouts that perform legitimacy without producing it are non-certifiable
- Is **stewardship-grade** — assurance is for stewards, not for sales

Legitimacy that cannot survive scrutiny in a real institution is not legitimacy.

---

## 2. Legitimacy Validation Domains

### 2.1 Deployment Realism
Validation that deployments operate in real institutional environments under governance:
- Production environments are doctrinally isolated from demo and pilot
- Release manifests reflect actual deployed state
- Stakeholder visibility actions are executed, not staged
- Continuity posture observation post-deployment is real and recorded

### 2.2 Pilot Realism
Validation that pilots are genuine bounded engagements:
- Pilot scope is structurally enforced, not merely declared
- Pilot data does not contaminate production
- Pilot exit is governed and reviewed
- Pilot duration is doctrinally disciplined; perpetual pilots are flagged

### 2.3 Continuity-Safe Modernization
Validation that modernization advances continuity-safely:
- Sequencing rationale on file
- Pacing aligned to absorption capacity
- Reversibility credible at each step
- Stakeholder trust observed through the sequence

### 2.4 Governance-Safe Rollout
Validation that rollouts honor governance:
- Each rollout stage earns the next via observation
- Concurrent change is within doctrinal ceilings
- Stakeholder communication is proportional to impact
- Rollback path is validated, not merely asserted

### 2.5 Organizational Trust Pacing
Validation that trust is built at institutional rhythm:
- Capability exposure paced to role-bearer absorption
- Governance forum cadence honored
- Workforce trust signals monitored
- Executive cognitive load remains within thresholds

### 2.6 Institutional Readiness
Validation that the receiving institution is ready for the change:
- Readiness assessment on file
- Role-bearer onboarding plan
- Governance forum integration
- Continuity surfaces accessible from day one

### 2.7 Operational Maturity Signaling
Validation that the operational mode of the system reads as institutional, not startup:
- Stable doctrinal vocabulary
- Calmness floors honored across surfaces
- Manifest discipline universal across releases
- Standing review cadence sustained

---

## 3. Validation Anti-Patterns

The following are categorical legitimacy failures. Their detection blocks certification at any tier.

- **Startup theater** — operating mode signals (motion, urgency framing, AI-hype UX, capability showcase) that mimic startup vendor posture
- **Demo instability** — demonstrations that depend on real production state, or production that bears traces of demo state
- **Governance ambiguity** — releases without clear governance authority, manifest, or reviewability
- **Deployment opacity** — releases whose included changes, sequencing, or rollback path are not documented in retained evidence
- **Uncontrolled rollout** — rollouts that proceed by calendar rather than by observation
- **Modernization chaos** — concurrent change exceeding institutional absorption, recovery interval violations, persistent rollback rate elevation

A system displaying any of these is not operationally legitimate, regardless of feature surface area.

---

## 4. Tiered Operational Legitimacy Assurance

| Tier | Evidence Threshold |
|------|--------------------|
| C0 | Unverified |
| C1 | Manifest discipline applied; named owners; governance forum identified |
| C2 | Realism, pacing, and rollout governance applied; partial automated evidence |
| C3 | Continuous evidence (manifests, sequencing, pacing, isolation) tied to release gates |
| C4 | Signed evidence retention; external reviewer can verify; standing review sustained; institutional trust signals monitored |
| C5 | Sustained C4; reference-grade institutional operating mode |

---

## 5. Validation Procedure

1. Subject and scope declared (system, deployment window, institution)
2. Validation domains evaluated with cited evidence from the [evidence pipeline](governance-evidence-pipeline-architecture.md)
3. Anti-patterns screened
4. Reviewer attestation
5. Tier determined per evidence threshold
6. Recording and standing-review scheduling

Anti-pattern detection is exit criteria; the validation does not proceed without remediation.

---

## 6. Trust Pacing Discipline

Operational legitimacy is not earned in a single release. Trust pacing is itself a validated dimension:

- New capability exposure rate respects absorption
- Governance forum integration deepens at institutional rhythm
- Workforce trust signals monitored as indicators (per aggregation stance)
- Executive cognitive load tracked over time
- Stakeholder communication backlog is bounded

Pacing that exceeds institutional rhythm — even with PASS verdicts on individual changes — is itself an indicator at the [scorecard](../nzila-governance/doctrine-governance-scorecard.md).

---

## 7. Anti-Patterns in Assurance Itself

- **Theater dressed as evidence** — staged demonstrations counted as legitimacy evidence
- **Per-release blindness** — assuring releases individually but missing accumulated pacing breach
- **Sales-driven legitimacy** — pursuing higher tier for procurement positioning rather than for institutional standing
- **Backfilled manifests** — manifests assembled after the deployment as evidence
- **Reviewer-rotation insufficiency** — same reviewer indefinitely

---

## 8. External Posture

Operational legitimacy assurance is presentable in:

- Procurement evidence packs (essential for institutional buyers)
- Regulator engagements where deployment governance is in scope
- Investor diligence (especially institutional capital)
- Standing readiness review

It is the assurance most directly answering: *"Is this software actually operating in real institutions, or does it merely demonstrate?"*

---

## 9. Discipline

Operational legitimacy is the property buyers most often misjudge in vendors and most need to verify. This assurance system is the institutional answer.

Its strength is the refusal to perform legitimacy: it is built, evidenced, and reviewed.
