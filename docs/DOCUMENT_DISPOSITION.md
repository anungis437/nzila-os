# Document disposition register

This register records, for each substantial documentation family in the repository, what role it
plays **today**. It exists because several large programme trees describe themselves as
"canonical authority" for a state captured months ago, and because some of them are read by
validators and therefore cannot be moved into the archive without breaking a gate.

Dispositions used here (one per family):

| Disposition                                                         | Meaning                                                                            |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `CURRENT AUTHORITY`                                                 | Owns a subject today. Change the system, then change this.                         |
| `CURRENT SUPPORTING DOCUMENTATION`                                  | Currently useful, but not the owner of its subject.                                |
| `MACHINE-CONSUMED EVIDENCE`                                         | Read by a script/validator/test; its shape is a contract.                          |
| `HISTORICAL — ARCHIVABLE`                                           | Record of a past state; nothing depends on its location.                           |
| `HISTORICAL — MUST REMAIN IN PLACE BECAUSE OF VALIDATOR DEPENDENCY` | Record of a past state that a validator resolves by path. Moving it breaks a gate. |
| `SUPERSEDED`                                                        | A newer authoritative artifact replaced it; retained for lineage.                  |
| `GENERATED`                                                         | Produced by a command; edit the generator, not the file.                           |
| `UNRESOLVED`                                                        | The repository does not currently establish its status.                            |

Rules this register follows:

- Historical bodies are not rewritten to match current conclusions. Where a document's own
  verdict is stale, a temporal banner is added above it; the body is left as written.
- Validator-dependent material stays where it is. The dependency is named below so a future
  reader knows what to repair before moving anything.
- Dates are taken from Git history for the path (first and last commit touching it), not from
  prose inside the documents.

## `full-*` analysis / refactor documents

There is no independent `full-*` family: every `full-*.md` in `docs/` is a member document of one
of the programme trees above (`nzila-tier2-hardening`, `nzila-infrastructure-convergence`,
`nzila-operational-proving`, `nzila-finalization`, `union-eyes/runtime-convergence`) plus
`docs/readiness/full-production-readiness-delta.md`. They inherit their tree's disposition. The
one non-doc match, `apps/union-eyes/scripts/rls-enforcement/full-migration-transactional-proof.ts`,
is code and out of scope for this register.
