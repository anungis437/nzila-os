---

## 1. Objective (verbatim)

> Harden every id-scoped route under `apps/union-eyes/app/api/pilot/apply/[id]/**`
> so no steward/officer can mutate, transition, export, or generate commercial
> artifacts for a pilot application unless the application belongs to their
> organization, or the actor is explicitly platform_admin / implementation_owner.

**Primary invariant:** A user cannot act on a pilot application by ID unless they
own that org scope or hold an explicit platform-level role. Ownership is verified
**before** any system-context operation, mutation, export, commercial transition,
proposal generation, or artifact package generation.

---

## 2. Pre-existing gap

The id-scoped pilot routes carried a role gate (`hasMinRole('steward')`) but **no
org-ownership check**. Because `pilot_applications` has no `organization_id`
column and the base item route is generated by the shared `crudRoutes()` factory
with `orgScoped: false`, any steward-or-above in **any** organization could read,
mutate, export, transition, or generate commercial artifacts for **any** pilot
application by guessing/holding its ID — a cross-org mutation/export/billing leak.

**Ownership signal used:** the canonical owning organization is carried in
`responses.organizationId` (a string inside the JSONB `responses` field) — the
same field the `commercial-transition` route already uses to resolve the billing
account. No schema change was made.

## 4. Ownership invariant — implementation

New helper: `apps/union-eyes/lib/pilot/pilot-ownership.ts` (single small,
reusable module — no factory or RBAC redesign).

- `getPilotOwnerOrganizationId(application)` — reads `responses.organizationId`;
  returns a trimmed non-empty string or `null` (fail closed).
- `authorizePilotAccess(pilotOrganizationId)` — resolves the actor via
  `getCurrentUser()` and returns a typed `PilotAccessDecision`. This is the pure,
  unit-testable decision core (all actor state comes from `getCurrentUser()`).
- `enforcePilotOwnership(application)` — convenience guard returning a
  `NextResponse` (401/403) on deny or `null` to proceed. Used by the 7 explicit
  routes after their own 404 check.
- `withPilotOwnership(handler, paramName='id')` — thin wrapper for the
  CRUD-factory base route: loads the pilot by `id` (selecting only `responses`),
  returns 404 if missing, enforces ownership, then delegates — **without** reading
  the request body (factory PATCH body parsing is preserved).

**Platform-level mapping (documented decision):** UE's role hierarchy has no
literal `platform_admin` / `implementation_owner` role. The platform-level
concept is the app-ops / system roles at level ≥ `ROLE_HIERARCHY.system_admin`
(**200**), plus `PLATFORM_ADMIN_USER_IDS` (resolved by `getCurrentUser()` to
`app_owner` = 300). The threshold constant `PILOT_PLATFORM_ACCESS_MIN_LEVEL`
is set to 200. **Org-level executives stay org-scoped** — `admin` (140),
`president` (130), `officer` (80), `steward` (50) are all below the platform line
and must match the pilot's owning org.

The existing per-route role gate (`hasMinRole('steward')`) was left unchanged.

## 7. Remaining / deferred risks (Phase 3+)

1. **`pilot_applications` lacks a first-class `organization_id` column** —
   ownership is inferred from `responses.organizationId` (JSONB). A proper column
   + backfill + FK would be sturdier than a JSON field. Deferred (schema/migration
   work, out of Phase 2 scope).
2. **`getCurrentUser().organizationId` fallback chain** can ultimately resolve to
   `DEFAULT_ORGANIZATION_ID` for users with no membership. This is a pre-existing,
   app-wide behavior **not introduced here**; it could weaken org scoping for
   membership-less identities. Flagged for Phase 3+ review.
3. **Raw DB guard classification** — explicitly out of scope (Phase 3). Not
   touched.
4. **Role gate breadth** — the per-route `hasMinRole('steward')` gate was left
   unchanged by design; no RBAC redesign performed.
