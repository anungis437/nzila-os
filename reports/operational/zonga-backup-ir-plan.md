## 2. Data Backup Strategy

### 2.1 PostgreSQL Database

**Backup Method**: Azure Database for PostgreSQL Flexible Server has **automated backups enabled by default**.

| Property | Value |
|---|---|
| Backup type | Automated (managed by Azure) |
| Retention period | 7 days (default) — **upgrade to 35 days for production** |
| Backup frequency | Full daily + transaction log every 5 minutes |
| Point-in-time restore | Yes — any point within retention window |
| Geo-redundant backup | **Configure before launch** |

**Recommended Change Before Launch**:

```bash
az postgres flexible-server update \
  --resource-group nzila-canada-staging-rg \
  --name nzila-staging-db \
  --backup-retention 35 \
  --geo-redundant-backup Enabled
```

**Manual Backup Procedure** (before major deployments):

```powershell
$env:PGPASSWORD = "nzila_dev"
$timestamp = Get-Date -Format "yyyy-MM-dd-HHmm"
& "C:\Program Files\PostgreSQL\17\bin\pg_dump.exe" `
  -U nzila -d nzila_automation -p 5433 -h <AZURE_HOST> `
  --format=custom `
  --file="backup-zonga-$timestamp.pgdump"
```

**Restore Procedure**:

```bash
# Option 1: Azure Portal — point-in-time restore
# Azure Portal → PostgreSQL Flexible Server → Restore

# Option 2: pg_restore from dump
pg_restore -U nzila -d nzila_automation_restore \
  --format=custom backup-zonga-<timestamp>.pgdump
```

### 2.2 Azure Blob Storage (Media)

- **Azure Blob Storage is the source of truth for all audio and image files.**
- Raw uploads are stored under `raw/{creatorId}/{contentAssetId}/{timestamp}.{ext}`
- Processed variants stored under `processed/` prefix
- **Blob versioning**: Enable soft-delete with 30-day retention

**Recommended Configuration Before Launch**:

```bash
az storage account blob-service-properties update \
  --account-name nzilacanadastore \
  --enable-delete-retention true \
  --delete-retention-days 30
```

**Media Recovery**: If processed variants are lost (e.g. MediaConvert failure), they can be regenerated by re-queuing the original raw upload through the processing pipeline. Raw files are the durable source.

### 2.3 Configuration / Secrets

All secrets are stored in Azure Key Vault. Backups:

- Source of truth: 1Password vault (shared with Nzila team)
- Key Vault provides soft-delete by default (90-day recovery window)
- GitHub Secrets are a secondary copy for CI/CD

## 4. Incident Response Runbook

### Step 1 — Detect

**Automated signals (configure before launch)**:

- Azure Monitor alert: Container App error rate >5% for 5 minutes
- Azure Monitor alert: DB connection failures >10 in 60s
- AWS CloudWatch: CloudFront 5xx rate >2%
- Uptime monitor: [UptimeRobot / Better Uptime] ping `/api/health` every 60s

**Manual check signals**:

- User report via support email / Discord / in-app feedback
- Failed payment Stripe webhook event

### Step 2 — Triage

1. Check Azure Portal → Container Apps → Log Stream for application errors
2. Check Azure Portal → PostgreSQL → Metrics for connection count / CPU
3. Check AWS Console → CloudFront → Error rate
4. Identify affected scope: all users / specific org / single creator

### Step 3 — Communicate

**Internal**: Post in Slack/Teams #incident channel:

```
[INCIDENT P{severity}] {date/time} — {brief description}
Status: INVESTIGATING
On call: {name}
```

**External**: If P0 or P1 impacting client, contact client via pre-agreed channel within 30 minutes.

### Step 4 — Contain

| Scenario | Containment Action |
|---|---|
| DB overload | `az postgres flexible-server restart` + scale vCores up |
| Container App crash loop | `az containerapp revision deactivate` previous + `az containerapp update --image <stable-tag>` |
| Storage outage | Switch playback fallback: set env var `ZONGA_FORCE_BLOB_FALLBACK=true` |
| Stripe webhook failures | Stripe Dashboard → retry failed webhook deliveries |
| Security breach | See Section 6: Security Incident Procedure |

### Step 5 — Resolve and Restore

1. Deploy fix or roll back to last known good image (see Section 5)
2. Verify via health endpoint and manual test
3. Clear any stuck processing queue jobs if DB was restarted

### Step 6 — Post-Incident

Within 48 hours:

- Write brief post-mortem (5-minute doc):
  - Timeline of detection → resolution
  - Root cause
  - Action items to prevent recurrence
- Store in `/docs/incidents/YYYY-MM-DD-title.md`

## 5. Rollback Procedure

### Application Rollback

Zonga is deployed as a Container App. All images are tagged and pushed to ACR.

```bash
# List recent image tags
az acr repository show-tags \
  --name nzilacanadaacr \
  --repository nzila-os-zonga \
  --orderby time_desc

# Rollback to a previous stable tag
az containerapp update \
  --name nzila-os-zonga \
  --resource-group nzila-canada-staging-rg \
  --image nzilacanadaacr.azurecr.io/nzila-os-zonga:<STABLE_TAG>
```

### Database Rollback

1. Create a restore server from the point-in-time backup
2. Validate data integrity
3. Update app's `DATABASE_URL` env var to point to restore server
4. Promote restore server to production

> ⚠️ **Never run migrations against production without a backup verified within the last hour.**

## 6. Security Incident Procedure

If a security breach is suspected:

### Immediate (0–15 min)

1. **Invalidate all active sessions**: `DELETE FROM auth_user_sessions WHERE created_at < NOW()` — effectively logs out all users
2. **Rotate auth secret**: Regenerate `AUTH_SECRET` and update in all Container Apps
3. **Notify Nzila security lead**

### Short Term (15–60 min)

4. Identify the attack vector from logs (Azure Log Analytics)
5. Block suspicious IPs at the Container Apps edge or via Azure Front Door (if configured)
6. Assess data exposure scope

### Regulatory Reporting

- GDPR: 72-hour notification to supervisory authority if EU users' data is breached
- POPIA (South Africa): notify Information Regulator within a reasonable time
- NDPR (Nigeria): 72-hour notification if ≥100 Nigerian users affected
- Notify affected users promptly once scope is known
