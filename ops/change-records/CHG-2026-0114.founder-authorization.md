## Entra tenant migration — real sign-in verification blocked; root cause narrowed, not yet resolved

Two dispatches of `ue-v2-staging-real-session.yml` against the current candidate both failed identically at `auth('A')`: the browser never leaves `login.microsoftonline.com` within the 120-second interactive-login budget, even though the explicit "more information required / approve sign in / enter code" text check (which would name the real cause) never matched — the loop simply times out. The password and UPN were independently re-verified correct (the Entra account's password was reset and the `UE_V2_STAGING_PERSONA_A_PASSWORD` environment secret updated to the exact same value in the same operation, with the Azure CLI's own exit code checked directly rather than through a filtering pipe, after an earlier false reading from exactly that mistake).

The first hypothesis tested was the new tenant's default-on "Security Defaults" (Microsoft's free MFA-enforcement baseline, automatically enabled on every new, non-Premium tenant): a dedicated, narrowly-scoped, temporary app registration was created and deleted again in the same session solely to obtain an app-only Microsoft Graph token (the Azure CLI's own first-party client is blocked by Microsoft from requesting Conditional-Access/Security-Defaults policy scopes at all, confirmed via `AADSTS65002`, independent of any tenant consent). That token confirmed Security Defaults was indeed `isEnabled: true` and was used to disable it. A third dispatch after this fix failed with the exact same symptom, ruling Security Defaults out as the (sole) cause.

The leading remaining hypothesis is Microsoft's own risk-based "unfamiliar sign-in" protection, which operates independently of Conditional Access/Security Defaults and cannot be disabled via tenant policy: brand-new Entra accounts in a two-week-old tenant, signing in for the first time ever from a GitHub-hosted runner's datacenter IP with zero prior sign-in history, are a textbook trigger for an interactive challenge (CAPTCHA/puzzle or similar) that a headless script cannot solve and that would not match the specific "more information required" MFA-registration text the script already checks for. This is consistent with every one of this record's many prior successful real-Entra runs having used accounts with weeks of established sign-in history in a different, older tenant. This hypothesis was not independently confirmed (sign-in logs are unavailable via Graph API on this tenant's non-Premium license, returning `Authentication_RequestFromNonPremiumTenantOrB2CTenant`; a local non-headless browser repro was attempted but blocked by a corrupted/incomplete local Playwright Chromium cache that did not fully resolve after multiple clean reinstall attempts in this environment).

No further tenant or application configuration change is recommended on this evidence alone. The practical next step is a one-time real, human-interactive sign-in for each new persona (likely resolves or disproves the risk-based-challenge hypothesis immediately) or allowing the accounts more time/usage history before the next automated attempt.
