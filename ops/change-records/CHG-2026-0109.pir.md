# CHG-2026-0109 — Post-Implementation Review

Change: EMERGENCY, HIGH risk, restore Union Eyes production. Window 2026-10-05 to 2026-10-07.
Outcome: **PARTIAL_SUCCESS**. Service restored; two follow-ups remain open and need their own change authority.

## Incident

Union Eyes production was unavailable. `unioneyes.app`, `www.unioneyes.app` and `app.unioneyes.app` returned 504 or timed out.

- Active revision `nzila-os-union-eyes-prod--0000247` (created 2026-09-19T14:30:51Z) was stuck in `ImagePullBackOff` on both replicas, with ~64,900 failed pulls logged.
- The previous revision `--0000246` (2026-09-19T04:32Z) ran the same image tag and was healthy when created.
- Restored at 2026-10-05T17:43:30Z: revision `--0000249`, image `nzila-os-union-eyes@sha256:2836e47a…` (tags: `c890d1a2d…`, `production`), 100% traffic.

Customer impact: availability was zero from no later than 2026-09-19T14:30Z until 2026-10-05T17:43Z (about 16 days). Request volume, affected organizations and any data impact are **not derivable from the evidence collected** and must be pulled from Front Door and application telemetry before this is closed with customers.

## Primary cause

The production image was unavailable in `nzilacanadaacr`. The tag `prod-continuity-managed-20260918-1245` still resolved, but its index referenced an amd64 child manifest (`sha256:96c6e302…`) that no longer existed. Every earlier production digest (`765d6515…`, `8e43602a…`, `e01ec91e…`) was also gone. Soft delete is disabled, so nothing was recoverable.

Why the images disappeared: **not established**. Evidence:

- Repo workflows that delete from ACR touch only `nzila-build-proof` and the legacy union-eyes repo. None touches `nzila-os-union-eyes`.
- No ACR tasks are defined, and the registry has no diagnostic settings, so there is no data-plane delete log. The Azure activity log does not record data-plane deletions.
- The registry is SKU Basic. Retention policies need Premium, so `reports/strategic/SPRINT_COMPLETION_2026-05-01.md` ("ACR retains 90-day image history (per retention policy)") describes a control that does not exist.
- Pattern consistent with an untagged-manifest purge: only digest-pinned, untagged images and the untagged children of the surviving index vanished. This is an inference, not proof.

## Contributing causes

1. **Expired change record.** The only prod record, CHG-2026-0108, ended 2026-09-27. `validate-change-window` correctly blocked the first deploy.
2. **Key Vault grants.** The prod deploy identity (`nzila-os-deploy-prod`) could read only `union-eyes-migration-admin-database-url`. The deploy treated four secrets as missing.
3. **Hostname drift.** The web build, DAST, DR drill, health proof, smoke URL and DNS fallback used `nzila-os-union-eyes.<env-domain>`, a Container App that does not exist (404). The production GitHub Environment variable `DNS_STAGING_ORIGIN` pointed at it too.
4. **Mutable, untagged production references.** Prod pinned images by bare digest, and the prod web app runs the mutable `nzila/web:latest`.

Correction to the earlier hand-off: the failed RLS preflight was **not** an observability problem. `rls-verify.ts` reported `FAILED (12 check(s) did not pass)` accurately; the 12 failures are real (below).

## Restoration

- Emergency change record CHG-2026-0109 (#911).
- Rebuild and digest-pinned deploy from main through `deploy-union-eyes.yml` run 37346351177. The ICRA capability migration and Django migrations applied.
- Least-privilege Key Vault access for the deploy identity.
- Hostname corrections (#910) and the production `DNS_STAGING_ORIGIN` variable.
- Staging web rebuilt and deployed through `gitops-deploy.yml`; its link now targets `nzila-os-union-eyes-staging` (307).

## RLS verification (open, blocking closure)

Direct reproduction of `rls-verify.ts --mode=preflight` against production with the intended runtime connection (read-only; temporary firewall rule created and removed) matched the deploy log.

- Runtime identity: connected as `union_eyes_runtime`; `rolsuper=false`, `rolbypassrls=false`.
- 1155 of 1167 checks passed. 12 failed.
- Class: **B** (expected RLS policy missing) **and C** (FORCE RLS missing) on the tables below. Not E (verifier defect) and not F or D (identity is correct).

|---|---|---|

The workflow's one-time rollout jobs are `if: false`, so they were never applied to prod. |
| `audit_logs`, `organization_users` | RLS off, FORCE off, no policies | Earlier migrations (`0058`, `0070`) target other schemas; enforcement for these public-schema tables still has to be confirmed. |

`PROD_RLS_DEFECT = YES`, `CHANGE_AUTHORITY_REQUIRED = YES`. CHG-2026-0109 covers restoring the service, not altering production database authority, so no database change was made. The RLS gate was not weakened.

## Prod web link (open)

`nzila-os-web-prod` still embeds the retired Union Eyes host. It runs `nzila/web:latest`, which now holds the staging build (it targets the staging Union Eyes container). Restarting prod web from `latest` would link prod to staging. A prod-specific build with `NEXT_PUBLIC_UNION_EYES_URL=https://app.unioneyes.app`, an immutable tag, SHA traceability and an environment gate is required. `deploy-production.yml` only promotes staging digests, so no governed prod web build exists yet.

## Rollback readiness

- Only the current production image remains in ACR (`sha256:2836e47a…`, tagged `c890d1a2d…` and `production`). It is a single-platform manifest with no untagged children, so it is not exposed to the same failure.
- **No prior production image exists**, so there is no rollback target for this release. This is the main residual risk until the next release is built and kept.

## Access review

`nzila-os-deploy-prod` now holds `Key Vault Secrets User` at secret scope on exactly: `union-eyes-runtime-database-url`, `union-eyes-system-database-url`, `resend-api-key`, `resend-webhook-secret`, plus the pre-existing `union-eyes-migration-admin-database-url`. No vault-wide grant was added. Pre-existing, unchanged: `Contributor` on `nzila-canada-prod-rg` and `AcrPull` on the registry.

During diagnosis the runtime database secret was read from Key Vault by the platform owner's account for a local, read-only preflight run. The secret was not printed or stored.

## What worked / what failed / what was manual

- Worked: fail-closed gates (change window, secret presence, digest pinning, RLS preflight) all stopped or flagged real problems.
- Failed: no alert fired for 16 days of total outage; no rollback image; documented retention control did not exist; prod change records were allowed to lapse.
- Manual: emergency workflow dispatch, secret-scoped role assignments via `az`, setting a GitHub Environment variable, two `gh run rerun --failed`, a staging web dispatch with an explicit version.
